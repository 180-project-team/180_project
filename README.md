## О проекте

Итоговый продукт — система для автоматической оптимизации LLM-агентов.

В систему загружается агент вместе с его конфигурацией, промптами, описаниями инструментов и информацией о структуре, а также набор задач, на которых можно оценить качество его работы.

В качестве основной предметной области используется агент для работы с документами: он ищет информацию в базе документов, анализирует найденные данные и формирует ответы на пользовательские запросы.

## Как работает система

### Локальное окружение

Из корня репозитория с установленным uv:

```shell
uv sync --locked
uv run --locked python -m unittest discover -s tests -v
uv run --locked python -m examples.diagnose_runner
```

Для загрузки вопросов напрямую из Hugging Face выполните
`uv sync --locked --extra huggingface`.

### Запуск SkimSearchAgent

Для корпуса документов нужен JDK 21 или новее. Укажите `JAVA_HOME` и установите
SkimSearchAgent из локального checkout в его окружение. Интеграция использует
Python API `build_agent()` из SkimSearchAgent 0.3.0.

```shell
uv venv --python 3.12 ../skim-search-agent/.venv
uv pip install --python ../skim-search-agent/.venv/bin/python -e '../skim-search-agent[api,retrieval]'
```

Подготовьте `corpus.jsonl` с одним документом на строку, например
`{"id":"python","title":"Python","text":"Python was created by Guido van Rossum."}`.
Вопросы передаются отдельно. В примере модель `qwen3:4b` уже доступна по указанному OpenAI-совместимому адресу.

```shell
uv run --locked python -m app --adapter skim \
  --skim-python ../skim-search-agent/.venv/bin/python \
  --skim-corpus corpus.jsonl --skim-model qwen3:4b \
  --skim-api-base http://127.0.0.1:11434/v1 \
  --questions data/evaluation_dataset.jsonl --limit 2 \
  --run-dir runs/skim --results-path runs/skim/runner_results.jsonl
```

По умолчанию адаптер использует стратегию `sieve_bm25` и готовит индекс в
`<run-dir>/skim_indexes` один раз на пакет. Для проверки запуска можно опустить
`--skim-model`, чтобы использовать тестовую политику SkimSearchAgent.

В Python оркестратор передаёт путь в `runner.run(questions, run_dir, results_path=...)`.
Runner записывает по строке на вопрос и публикует готовый JSONL после полного
обхода итератора. В [`examples/orchestrator_demo.py`](examples/orchestrator_demo.py)
метод `execute()` завершает обход перед возвратом. Тот же путь можно передать в Evaluator и Diagnostics.

### Результаты запуска

Система запускает агента на подготовленных задачах и сохраняет:

- итоговые ответы;
- полные траектории выполнения;
- промежуточные шаги;
- вызовы инструментов;
- результаты вызовов;
- возникающие ошибки.

Результат каждого запуска оценивается отдельным модулем по заданным метрикам качества.

Модуль Diagnostics читает JSONL Runner и Evaluator через `diagnose_run()`.
Он сохраняет наблюдаемые нарушения, свидетельства и гипотезы для проверки
в `diagnoses.jsonl` и `summary.json`. В целевой архитектуре отчёты передаёт
оптимизатору оркестратор. [Контракты и примеры Diagnostics](app/diagnostics/README.md)

Оптимизатор L1 принимает путь к готовой диагностике, каталог вывода и обычную
строку с кодом и структурой агента. Общий LLM-клиент передаётся извне.
Он сохраняет prompt patch и кандидат для последующего запуска и оценки общими
модулями. [Интерфейс L1 и ограничения интеграции](docs/prompt_optimizer.md)

После каждого изменения новая версия агента снова проверяется на наборе задач и сравнивается с предыдущей. Изменения, которые действительно улучшают качество на отложенных данных, сохраняются, неудачные изменения отклоняются. Оптимизация продолжается до тех пор, пока качество растёт или пока не выполняется заданное условие остановки.

## Уровни оптимизации

### 1. Текстовые параметры

Изменяются промпты, описания инструментов и другие текстовые параметры агента.

### 2. Структура и обвязка

Изменяются управление контекстом и памятью, проверки, повторные попытки, маршрутизация и другие дополнительные компоненты.

### 3. Архитектура и программная реализация

Подключается кодовый агент, который может менять архитектуру и программную реализацию: добавлять новые узлы, инструменты и связи между компонентами.

## Режимы работы

Система поддерживает несколько режимов работы:

- можно выбрать только один тип оптимизации, например изменение промптов или структуры;
- можно разрешить несколько уровней одновременно;
- предусмотрен полностью автоматический режим, в котором система сама определяет причину ошибки и выбирает подходящий уровень изменения.
