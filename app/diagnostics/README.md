# Diagnostics: API и ограничения MVP

Документ описывает реализованный пакет `app/diagnostics/`. Архитектурные цели
и полная классификация приведены в [спецификации](../../docs/diagnostics.md); не все её
возможности входят в текущую реализацию.

## Запуск примера

Из корня репозитория:

```shell
python -m examples.diagnose_runner
```

Пример использует настоящий `AgentRunner` и искусственный локальный агент.
Модель, GPU, сетевые сервисы и дополнительные зависимости не нужны.
В stdout выводится JSON со списком записей Runner в поле `runner` и результатом
диагностики в поле `diagnostics`.

Пять сценариев демонстрируют обычный ответ, пустой ответ, исключение агента,
ошибку инструмента при успешном завершении и повтор поиска. Ожидаемый результат:
5 проанализированных задач, 3 задачи с наблюдаемыми ошибками и 1 предупреждение
о повторе поиска. У одной записи Runner статус `error`. Диагностика также
обнаруживает нарушения в записях со статусом `ok`.

## Вызов из Orchestrator

```python
import json
from dataclasses import asdict

from app.diagnostics import diagnose

# Runner, вопросы, каталог и идентификатор запуска предоставляет вызывающая сторона.
rows = runner.run(questions, run_dir)
batch = diagnose(
    rows,
    run_id=run_id,
    version_id="agent-v1",
)
serialized = json.dumps(asdict(batch), ensure_ascii=False)
```

`AgentRunner.run()` возвращает итератор записей. `diagnose()` обрабатывает записи
по мере поступления. За сохранение результатов Runner и отчётов Diagnostics
отвечает вызывающая сторона.

## Входной контракт

`diagnose_case(case)` принимает JSON-строку или уже разобранный объект и
возвращает `DiagnosisReport`. Пример входа:

```json
{
  "case_id": "question-1",
  "question": "Where was the director born?",
  "answer": null,
  "status": "error",
  "evaluation_status": "error",
  "trajectory": null,
  "metrics": {"fact_recall": null},
  "error": "Tool timed out"
}
```

Идентификаторы и поля `error` и `traceback` опциональны. Значение
`status` должно быть `ok`, `error` или `unknown`. Метрики относятся
к одному вопросу. Для отсутствующей оценки используется `null`, а при
отсутствии всех метрик можно передать пустой объект. Некорректный вход
приводит к `ValueError`. Пути свидетельств отсчитываются от входного объекта.

Пакетный интерфейс для результатов Runner:

```python
diagnose(
    results: Iterable[Mapping[str, Any]],
    *,
    run_id: str | None = None,
    version_id: str | None = None,
    normalizer: Callable[[Mapping[str, Any]], Sequence[TraceEvent]] = normalize_trace,
    answer_validator: Callable[[Any], bool] | None = None,
    quality_thresholds: QualityThresholds = QualityThresholds(),
    classifier: FailureClassifier | None = None,
) -> DiagnosisBatchResult
```

- `results` — итератор из `AgentRunner.run()` или другой итерируемый набор совместимых
  отображений. Для каждой записи создаётся один отчёт в исходном порядке.
- `id` переносится в `case_id` без преобразования. Допустимы `str`, `int`, `None`;
  отсутствующий идентификатор остаётся `None`. Runner сам преобразует свои ID в строки
  и создаёт их при отсутствии в заданиях; Diagnostics сохраняет уже полученное значение.
- `status`, `answer`, `error` и `trajectory` используются при наличии.
  Статус Evaluator передаётся в `evaluation_status`, оценки — в поле `metrics`.
- `run_id` и `version_id` имеют тип `str | None`. Аргументы функции имеют приоритет
  над одноимёнными полями записей. Отсутствующие значения не генерируются.
- Входные данные не изменяются. Модели используют `dataclass` и аннотации типов;
  полноценной проверки схемы входа во время исполнения нет.

Пустая пачка возвращает пустой список отчётов и сводку с нулевыми счётчиками.

### Загрузка артефактов Runner и Evaluator

```python
from app.diagnostics import diagnose, load_diagnostic_cases

cases = load_diagnostic_cases(run_results_path, evaluation_results_path)
batch = diagnose(cases)
```

`load_diagnostic_cases()` принимает два явно заданных пути `str` или `Path`
к UTF-8 JSONL. Абсолютные пути можно передавать из любого рабочего каталога.
Пустые строки пропускаются. Остальные строки должны содержать JSON-объекты
со статусом `ok` или `error`. В записи Runner нужен непустой вопрос.
Если передана траектория, её значение должно быть массивом или `null`.

Строковые и целочисленные `id` приводятся к `str(id).strip()`. Пустые ID,
логические значения и дубликаты после приведения вызывают `ValueError`.
Оба файла должны содержать одинаковый непустой набор ID. При расхождении
ошибка перечисляет недостающие ID для каждого файла. Порядок записей Runner
сохраняется.

В объединённой записи нормализованный `id` становится `case_id`. Остальные
поля Runner, включая `status`, `duration_ms` и `trajectory`, сохраняют свои
пути. `evaluation_status`, `metrics` и `execution_metrics` заполняются полями
Evaluator. `execution_metrics` содержит доступные `duration_ms` и счётчики
вызовов инструментов Evaluator. Поля `case_id`, `evaluation_status`, `metrics`
и `execution_metrics` зарезервированы адаптером. При их наличии во входной
записи Runner загрузка сообщает о конфликте. Оценки переносятся как есть,
включая `null`, ноль и некорректные значения. Их обрабатывает `diagnose()`.

Чтобы восстановить свидетельство, загрузите ту же пару файлов, выберите
запись с `case_id` отчёта и пройдите по `EvidenceRef.path`. Происхождение
типичных путей указано в таблице.

| Путь в объединённой записи | Поле исходной записи с тем же нормализованным ID |
| --- | --- |
| `["trajectory", 0, "observation"]` | `trajectory[0].observation` в Runner |
| `["metrics", "fact_recall"]` | `fact_recall` в Evaluator |
| `["evaluation_status"]` | `status` в Evaluator |

### Метрики Evaluator

`fact_recall` оценивает полноту ответа по эталонным фактам, `fact_precision` —
соответствие утверждений ответа эталонным фактам. `retrieval_fact_recall` оценивает
покрытие эталонных фактов успешными наблюдениями инструментов. `faithfulness`
оценивает подтверждённость утверждений ответа этими наблюдениями. Финальный
контекст модели остаётся отдельным источником данных.

Эвристический порог для каждой метрики по умолчанию равен `0.8`. Равенство порогу
считается достаточным. Пороги настраиваются через `quality_thresholds=QualityThresholds(...)`.
Допустимы числа в диапазоне `[0, 1]`, включая `0.0`. Пропущенное поле означает
отсутствие данных, `null` — явное отсутствие оценки. `diagnose()` отмечает
некорректные оценки предупреждением `invalid_quality_metrics`, а `diagnose_case()`
выбрасывает `ValueError` при некорректном входе.

| Наблюдение | Проверяемые гипотезы |
| --- | --- |
| Низкие `fact_recall` и `retrieval_fact_recall` | Проверить, каких фактов не хватает в ответе и наблюдениях инструментов |
| Низкий `fact_recall` при достаточном `retrieval_fact_recall` | Проверить полноту ответа, интерпретацию найденных фактов и, при наличии, фактический контекст финальной модели |
| Низкий `faithfulness` | Сопоставить утверждения ответа с инструментальными наблюдениями |
| Низкий `fact_precision` при достаточном `faithfulness` | Проверить, относятся ли дополнительные подтверждённые детали к вопросу и эталонным фактам |
| Низкие `fact_precision` и `faithfulness` | Проверить подтверждённость и корректность спорных утверждений |

Для низких оценок без установленной причины отчёт возвращает `UNKNOWN` с
гипотезами. Оценки без выявленных проблем сами по себе не подтверждают
правильность ответа. При `evaluation_status="error"` Diagnostics отмечает
ошибку оценки и продолжает проверять наблюдения Runner.

### Опциональная классификация через API

`LLMClassifier` принимает готовый `LLMService`. Вызывающая сторона управляет
жизненным циклом сервиса.

```python
from app.diagnostics import LLMClassifier, diagnose_case
from app.llm import LLMService

with LLMService(model="local-model") as llm_service:
    report = diagnose_case(case, classifier=LLMClassifier(llm_service))
```

Без явно переданного классификатора все проверки выполняются локально.

При низкой оценке Evaluator и обоснованной гипотезе возможен один вызов API.
Для него нужны вопрос, пригодный для анализа ответ и хотя бы одно содержательное
наблюдение успешного инструмента. При установленной ошибке формата ответ
обрабатывается локально. Ранее замеченная техническая ошибка инструмента
сохраняется отдельным сигналом при анализе качества ответа.

Сервис получает вопрос и ответ длиной до 2000 символов каждый, готовые метрики,
до восьми сигналов и гипотез и до восьми целевых шагов с исходными индексами.
Выборка сохраняет ранние и поздние наблюдения и учитывает ссылки сигналов
и шаги чтения документов.
Наблюдения ограничены 1200 символами, поисковые запросы — 320. Поля `raw_output`
и `traceback` исключаются, распознаваемые учётные данные в тексте маскируются.

Категории в запросе следуют из сигнала качества. `UNKNOWN` доступен и при
единственной гипотезе. Оценки, выдержки из наблюдений и гипотезы передаются
как анализируемые данные. Недоступный финальный контекст ограничивает выводы
о потерянной информации.

Принятая категория добавляет `classifier_selection` с низкой уверенностью,
ссылками на метрики и наблюдения и пустым `critical_step`. Установленная
техническая ошибка уровня `FAILURE` сохраняет приоритет в отчёте. При
`UNKNOWN`, некорректном ответе или исключении локальный отчёт дополняется
только `classifier_attempt`. При использовании `LLMClassifier` стоимость
вызова остаётся `null`.

## Выходной контракт

`DiagnosisBatchResult` содержит `reports: list[DiagnosisReport]` и
`summary: DiagnosisSummary`. Для JSON используется `dataclasses.asdict`:
перечисления наследуются от `str`, а отсутствующие значения сериализуются как `null`.

### Отчёт задачи

| Поле | Значение |
| --- | --- |
| `case_id`, `run_id`, `version_id` | Связь с исходной задачей и запуском |
| `status` | Результат диагностического прохода, см. таблицу ниже |
| `failure_type` | Основная категория или `UNKNOWN` |
| `critical_step` | Предполагаемый проблемный шаг или `None` |
| `evidence_refs` | Объединение ссылок на свидетельства всех сигналов без дублей |
| `rationale` | Краткое объяснение основной категории и ограничений локализации |
| `confidence` | `low`, `medium` или `high`; не вероятность |
| `suggested_scope` | Подсказка области проверки: `PROMPT`, `STRUCTURAL`, `CODE`, `UNKNOWN` |
| `signals` | Все полученные сигналы, включая предупреждения |
| `hypotheses` | Гипотезы для основной категории с полями `hypothesis_id`, `scope`, `advice` |
| `classifier_attempt` | Статус вызова классификатора и стоимость, если её сообщил сервис |

При основной технической ошибке `suggested_scope` отражает её область проверки.
Дополнительная семантическая гипотеза может относиться к другой области.
Prompt Optimizer ориентируется на `suggested_scope` основного отчёта.

| Статус | Условие |
| --- | --- |
| `FAILURE_FOUND` | Есть хотя бы один сигнал уровня `FAILURE` |
| `NO_FAILURE_DETECTED` | Нет таких сигналов, Runner вернул `status="ok"` |
| `INSUFFICIENT_DATA` | При отсутствии выявленных ошибок Runner не подтвердил успешное завершение или Evaluator сообщил об ошибке оценки |
| `DIAGNOSTIC_ERROR` | Исключение нормализатора, валидатора или формирования отчёта |

`NO_FAILURE_DETECTED` не подтверждает правильность ответа. `FAILURE_FOUND` означает
наличие наблюдаемой ошибки: ошибка инструмента остаётся в отчёте даже после
успешного завершения агента. Она не объявляется доказанной причиной неверного ответа.

Сигнал содержит `rule_id`, `failure_type`, `level`, `step_index`, `evidence_refs`,
`rationale`, `confidence` и опциональный `component_id`. Основным становится первый
сигнал уровня `FAILURE` с конкретной категорией. Если такой сигнал отсутствует,
отчёт использует первый сигнал уровня `FAILURE`. Предупреждения доступны в `signals`.

### Свидетельства и шаги

`EvidenceRef.path` — путь относительно соответствующего исходного результата.
Если исходные результаты сохранены в списке `rows`, значение можно получить так:

```python
value = rows[report_index]
for part in batch.reports[report_index].evidence_refs[0].path:
    value = value[part]
```

Например, `["trajectory", 0, "observation"]` указывает на результат
инструмента в первом шаге Skim. Если ответ отсутствует, свидетельство ссылается
на существующий `status`, подтверждающий завершение, а не на отсутствующее поле.

`step_index` и `critical_step` — индексы массива `trajectory` с нуля.
События из итоговых полей имеют неизвестный шаг.
`case_id` идентифицирует задачу. Локальный `event_id` выводится из пути события,
а `tool_call_id` связывает вызов и результат внутри этой траектории.

Для остановки Skim по лимиту критический шаг указывает на шаг `budget`, если
он зафиксирован в траектории.
Для ошибки инструмента шаг назначается при `status="error"`, единственном сигнале
ошибки инструмента на последнем наблюдаемом шаге и отсутствии на этом шаге финального
ответа или результата инструмента без ошибки. Это консервативная эвристика кандидата,
а не доказательство причинности. В остальных случаях возвращается `None`.

### Сводка

- `analyzed_cases` — число отчётов, включая недостаток данных и ошибки диагностики.
- `failed_cases` — число отчётов `FAILURE_FOUND`, включая наблюдаемые ошибки инструментов
  в успешных запусках; это не число неправильных ответов.
- `failure_counts` — распределение по одной основной категории на такую задачу.
- `report_indices` — индексы всех отчётов в `batch.reports`.
- `patterns` — одинаковое правило с одинаковыми категорией и уровнем в двух или более
  отчётах одного запуска и версии. Один отчёт учитывается в паттерне один раз.
  Паттерны предупреждений сохраняют уровень `WARNING`.
- `run_id`, `version_id` — общее значение соответствующего поля, если оно одинаково
  у всех отчётов; иначе `None`.

Паттерн содержит правило, категорию, уровень, идентификаторы запуска и версии,
а также `report_indices`. Индексы позволяют различать отчёты даже с повторяющимися
или отсутствующими `case_id`. В смешанной пачке общие счётчики охватывают всю пачку,
а источники доступны через отчёты. При неизвестных ID различить реальные запуски
невозможно: для агрегации нескольких запусков следует явно передавать идентификаторы.

## Реализованные правила

| Правило | Условие | Сигнал |
| --- | --- | --- |
| `execution_error` | Runner вернул `status="error"` | `FAILURE`, `UNKNOWN`, `high` |
| `tool_error` | Нормализованный результат инструмента содержит непустую ошибку | `FAILURE`, `TOOL_EXECUTION_FAILURE`, `medium` |
| `missing_answer` | `status="ok"`, ответ отсутствует, `None`, пустая строка/строка из пробелов или пустая коллекция `list`/`dict`/`tuple` | `FAILURE`, `OUTPUT_FORMAT_ERROR`, `high` |
| `invalid_answer` | Непустой ответ успешного запуска отклонён переданным валидатором | `FAILURE`, `OUTPUT_FORMAT_ERROR`, `high` |
| `repeated_search` | Непустой поисковый запрос повторился точно, без нормализации регистра/пробелов | `WARNING`, `INEFFICIENT_LOOP`, `low` |
| `invalid_tool_call` | Skim сообщил о неразбираемом вызове или неверной ссылке на документ | `INVALID_TOOL_CALL` |
| `budget_stop` | Skim указал `max_steps`, `max_turns` или `ctx_budget` | `FAILURE`, `PREMATURE_STOP` |

После успешного повтора `bm25_search` с теми же аргументами ошибка поиска
сохраняется как предупреждение со ссылками на обе попытки.

Без валидатора произвольный непустой ответ не считается нарушением формата.
Например, `0` и `False` допустимы. Проверка не интерпретирует смысл текста,
не проверяет элементы непустого массива и не определяет правильность фактов.

Повторы поиска считаются по вызовам инструмента. Если нормализатор
возвращает только результаты, проверка использует запросы из этих результатов.

Область исправления берётся из каталога гипотез. Например,
`OUTPUT_FORMAT_ERROR` сопровождается проверкой формата ответа и областью
`PROMPT`, а `TOOL_EXECUTION_FAILURE` — проверкой доступности инструмента
и области `STRUCTURAL`.

## Расширение API

### Известный формат ответа

```python
batch = diagnose(
    runner.run(questions, run_dir),
    answer_validator=lambda answer: (
        isinstance(answer, list) and all(isinstance(item, str) for item in answer)
    ),
)
```

Валидатор должен возвращать `bool` и не изменять ответ. Он вызывается только для
непустого ответа при `status="ok"`. Исключение превращает отчёт задачи в
`DIAGNOSTIC_ERROR`, а не в ошибку агента. Такой отчёт не сохраняет частичные сигналы.

### Другой формат траектории

Передайте `normalizer=my_normalizer`. Функция принимает один результат и возвращает
последовательность `TraceEvent`. Пути `payload_ref` и `error_ref` должны указывать
на существующие данные этой записи. Для правил поиска нужны `search_query`,
для ошибок инструментов — событие `TOOL_RESULT` с `error_ref`. Diagnostics доверяет
контракту нормализатора и не проверяет разрешимость произвольных пользовательских ссылок.

Стандартный формат Skim Search использует `action`, `args`, `query`,
`observation`, `hit_ids` и `read_ids`. Для поискового запроса берётся первая
непустая строка из `args.query`, `args.q` и `query` в этом порядке. Вызов и его
наблюдение имеют общий `tool_call_id`. Завершающие и служебные шаги сохраняются
как `MODEL_RESPONSE`, а `FINAL_ANSWER` указывает на поле `answer` результата
Runner. Записи без достаточных признаков действия сохраняются как `UNKNOWN`.
Полный вход финальной модели может отсутствовать.

Для отдельных проверок доступны `normalize_trace(result)` и
`check_rules(result, events, answer_validator=...)`. В отличие от `diagnose`,
прямой вызов `check_rules` передаёт исключения валидатора вызывающему коду.

## Ограничения интеграции и MVP

- Если ответ адаптера содержит верхнеуровневый `error`, Runner сохраняет
  ошибку выполнения. Частичную траекторию и `traceback` из отдельного
  артефакта можно передать напрямую в `diagnose_case`.
- Отсутствующая траектория не мешает проверять статус и ответ. Успешный непустой
  ответ без траектории может получить `NO_FAILURE_DETECTED`, но локализация причин
  и семантическая оценка такого ответа недоступны.
- `TOOL_EXECUTION_FAILURE` означает явную ошибку результата инструмента.
  Более поздний результат того же инструмента сохраняется как дополнительное
  свидетельство. Если поиск с тем же запросом и аргументами вернул результат,
  ошибка сохраняется как предупреждение. Влияние на итоговый ответ остаётся
  неизвестным.
- Правила качества опираются на метрики и доступные свидетельства. Проверка
  цитирования и семантическая интерпретация остаются за границами правил.
- Расчёт метрик, кластеризация, хранилище и автоматический выбор оптимизатора
  выполняются вне пакета диагностики.
- Неподдерживаемые типы идентификаторов находятся вне входного контракта.
  Элемент пачки, не являющийся отображением, вызывает `TypeError`;
  исключение итератора пачки также передаётся вызывающему коду.

## Проверка

```shell
python -m unittest discover -s tests -p 'test_diagnostics*.py' -v
python -m unittest discover -s tests -v
```

Тесты используют искусственные данные, локальных агентов и подставной клиент API.

Размеченный контрольный набор содержит синтетические записи Runner с готовыми
оценками в формате Evaluator. Запустить сравнение можно следующей командой.

```shell
uv run --locked python -m examples.compare_skim_diagnostics tests/fixtures/skim_diagnostic_cases.jsonl
```

Команда сообщает точность категорий и критических шагов, а также долю
неопределённых результатов. Для сравнения правил с гибридным режимом передайте
классификатор в `compare(cases, classifier=...)`. В гибридном режиме сводка также
учитывает частоту вызовов и стоимость, если её сообщил сервис.
Для измерений на реальных данных каждая JSONL-строка
должна содержать `case` с объектом входного контракта,
а также размеченные `failure_type` и, если известен проблемный шаг, `critical_step`.
