# Интерфейс оптимизатора промптов L1

Основной вход оптимизатора — готовая диагностика команды и строка с исходным
кодом агента. Runner, Evaluator и Diagnostics не запускаются внутри оптимизатора.
Общий оркестратор управляет их вызовами, применением patch и принятием кандидата.

## Вызов из оркестратора

```python
from app.prompt_optimizer import PromptOptimizer

# Оркестратор создал и запустил общий app.llm.LLMService.
optimizer = PromptOptimizer(llm_service)
result = optimizer.optimize(
    diagnosis_path="runs/v1/diagnostics/diagnoses.jsonl",
    output_dir="runs/v1/prompt_candidate",
    agent_code=agent_structure_and_source,  # обычная строка
)

if result.status == "proposed":
    candidate_snapshot = result.candidate_code
    # Оркестратор связывает snapshot с файлами агента, запускает Runner
    # и Evaluator и принимает либо отклоняет кандидата.
```

LLM передаётся при создании сервиса; у `optimize()` ровно три входных аргумента.
Оптимизатор не создаёт модель и не управляет временем жизни переданного клиента.
Для тестов вместо клиента передаётся `generator=...` с методом
`generate(agent_code, reports)`.

## Диагностика

Поддерживаются `diagnoses.jsonl` из `diagnose_run()` и JSON одного
`DiagnosisReport`. `summary.json` не содержит отдельных диагнозов и отклоняется.
Исходные отчёты не изменяются. В генератор попадают отчёты со свидетельствами
и подходящими гипотезами `scope="PROMPT"`. Ошибки диагностики и записи
`INSUFFICIENT_DATA` не используются для генерации.

По умолчанию учитываются также дополнительные PROMPT-гипотезы при основной
категории STRUCTURAL, CODE или UNKNOWN. При необходимости оркестратор задаёт
`PromptOptimizer(llm_service, primary_scope_only=True)`. В этом режиме
используются только отчёты с основным `suggested_scope="PROMPT"`.
Номера `report_index` относятся к исходному порядку отчётов и начинаются с нуля.

## Строка с кодом и проверка patch

Строка может включать дерево файлов, заголовки и склеенные Python-исходники.
Отдельный PromptState и специальный JSON-формат упаковки кода не требуются.
Модель выбирает точный уникальный фрагмент исходной строки и предлагает его
замену. Фрагмент должен охватывать полные строки и полные Python-операторы.

В первой версии поддерживаются строковые литералы в присваиваниях и аргументах
с именами `prompt`, `instructions`, `template`, `description` и их вариантами
с подчёркиваниями; содержимое chat messages; PromptTemplate; описания `@tool`.
Поддерживаются обычные строки, f-строки и шаблоны с `.format()`.
Для проверки границ строк snapshot должен допускать Python-токенизацию.

Проверка сравнивает Python AST и текст вне разрешённых литералов, сохраняет
выражения f-строк и защищённые элементы в фигурных скобках/percent placeholders.
Изменения исполняемой логики, неоднозначный фрагмент, изменение переменных,
подмена примера в комментарии или строке документации и пустая правка отклоняются.
Snapshot привязывается к patch через SHA-256, чтобы не применять его к другой
версии. Исходный код не выполняется и файлы агента не перезаписываются.

Динамически загружаемые или собираемые промпты и другие языки в эту версию
проверки не входят. При отсутствии подходящего литерала генератор может вернуть
`{"no_change": true, "reason": "..."}`. Нужный prompt adapter добавляется отдельно.

## Выходные файлы

| Файл | Содержимое |
| --- | --- |
| `patch.json` | Статус, обоснование, хеши, ссылка на выбранный диагноз и точная замена `before` → `after` |
| `candidate_code.txt` | Строка кандидата; при отсутствии валидного patch — исходная строка |
| `changes.diff` | Разница двух строк snapshot для просмотра; пустая, если patch не предложен |

Авторитетный формат применения — `patch.json`, включая хеш исходного snapshot,
символьные смещения `start`/`end` и точный исходный фрагмент. `changes.diff`
использует условное имя `agent_snapshot.txt`; это не готовый git patch по файлам
репозитория. Восстановление файлов по snapshot остаётся за оркестратором.

`proposed` означает, что patch прошёл локальные проверки и ожидает внешней оценки.
`skipped` означает отсутствие подходящей гипотезы или обоснованный отказ генератора.
`rejected` означает невалидное предложение; `error` — ошибку генератора/LLM.
Отсутствие patch выражается через `patch: null`; качество не подменяется нулём.
Повторный вызов заменяет три файла целиком, очищая предыдущий diff и кандидата.
Файлы публикуются через временные файлы, manifest — последним. Для параллельных
вызовов нужны разные каталоги. Ошибки чтения входа и публикации передаются вызывающему.

## CLI

```shell
uv run --locked --python 3.12 python -m app.prompt_optimizer \
  --diagnosis runs/v1/diagnostics/diagnoses.jsonl \
  --output-dir runs/v1/prompt_candidate \
  --agent-code-file agent_snapshot.txt \
  --model qwen3:8b --base-url http://127.0.0.1:11434/v1
```

`--agent-code-file` только считывает текст и передаёт его третьим аргументом.
Вместо него можно передать обычную строку через `--agent-code`.
Для внешнего LLM ключ берётся из переменной, указанной в `--api-key-env`.
Самостоятельный CLI владеет своим LLM-клиентом; вызов сервиса из оркестратора — нет.

Проверка интерфейса без модели:

```shell
uv run --locked --python 3.12 python -m examples.prompt_optimizer_interface
uv run --locked --python 3.12 python -m unittest discover -s tests -p "test_prompt_optimizer*.py" -v
```

Пример использует настоящую Diagnostics для подготовки тестового входа и
фиксированный генератор правки. Он проверяет обмен артефактами, без оценки
улучшения качества агента.

Семантика отсутствующих метрик в необязательных утилитах чтения/сравнения
внешних оценок описана в [обзоре модуля](prompt_optimizer.md).
