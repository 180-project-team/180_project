# Структура FastAPI-сервиса

Документ описывает общие правила организации кода в проекте и структуру FastAPI-сервиса.  
Структура может меняться по мере развития сервиса, но общие принципы организации кода сохраняются.

---

## 1. Основные правила организации кода

### 1.1. Уровни приложения

Код делится на несколько верхнеуровневых частей:

```text
api
  ↓
modules
  ↓
common
  ↓
models
  ↓
core
```

Стрелки показывают допустимое направление зависимостей между уровнями, а не последовательность вызовов.

Простое правило: **нижний уровень не должен импортировать верхний**. Верхний уровень при необходимости может использовать код из расположенных ниже уровней.

### 1.2. Отношения между модулями

Каждый модуль содержит отдельную часть функциональности приложения.

Модули не должны напрямую управлять друг другом. Если нескольким модулям нужен один и тот же компонент, такой компонент выносится в `common`.

Если требуется объединить работу нескольких модулей в один процесс, координация выносится в отдельный модуль, а не размещается внутри одного из участвующих модулей.

### 1.3. `common`

`common` содержит компоненты, которые используются несколькими модулями и не относятся к логике одного конкретного модуля.

Например:

```text
common/
├── llm/            # общая инфраструктура работы с основной LLM сервиса
├── entities/       # структуры данных, используемые несколькими модулями
├── enums.py        # перечисления, используемые в нескольких частях приложения
└── exceptions.py   # исключения, общие для нескольких модулей
```

Если компонент используется только одним модулем, он должен оставаться внутри этого модуля.

### 1.4. Схемы API и внутренние сущности

Для разных типов данных используются разные части структуры:

- `schemas` — модели API-эндпоинтов: входные данные запросов и формы ответов;
- `models` — ORM-модели таблиц БД;
- `entities` — внутренние структуры данных и внутренние классы, используемые логикой приложения.

Модели API находятся рядом с соответствующими обработчиками:

```text
api/endpoints/<module>/schemas.py
```

Внутренние сущности размещаются внутри соответствующего модуля или в `common/entities/`, если используются несколькими модулями.

Код из `modules` не должен импортировать схемы из `api`.

### 1.5. Зависимости

Зависимости сервисов создаются и передаются извне.

FastAPI-зависимости находятся в:

```text
api/dependencies/
```

Долгоживущие ресурсы приложения создаются при запуске сервиса и затем передаются туда, где они нужны.

К таким ресурсам могут относиться:

- подключение к БД;
- фабрика сессий БД;
- общий LLM-клиент;
- HTTP-клиенты;
- другие подключения и ресурсы приложения.

### 1.6. Импорты

Используются абсолютные импорты от `app`.

```python
from app.modules.orchestrator.service import Orchestrator
from app.core.config import settings
```

Относительные импорты вида `from .module` и `from ..module` не используем.

### 1.7. База данных

ORM-модели находятся в `models/`.

`models` содержит Python-описания таблиц и связей БД, а не сами данные.

После подключения БД:

- базовый класс SQLAlchemy размещается в `models/base.py`;
- модели таблиц размещаются в `models/`;
- миграции размещаются в `migrations/`.

## 2. Схема работы сервиса

Основной путь запроса:

```text
HTTP-запрос
    │
    ▼
app/api/endpoints/optimization/router.py
    │
    ▼
app/api/dependencies/
    │
    ▼
app/modules/optimization_pipeline.py
    │
    │ run_pipeline(...)
    ▼
app/modules/orchestrator/
    │
    ├────────► app/modules/runner/
    ├────────► app/modules/evaluator/
    ├────────► app/modules/diagnostics/
    ├────────► app/modules/optimizer/
    └────────► другие модули
                    │
                    ▼
                 результат
```

`modules/optimization_pipeline.py` содержит верхнеуровневый код оркестрации процесса, в том числе `run_pipeline(...)`.

Вспомогательные части оркестратора, которые не нужно размещать в одном файле, находятся в `modules/orchestrator/`.

Создание ресурсов приложения выполняется отдельно:

```text
run_server.py
    │
    ├── FastAPI-приложение
    ├── lifespan
    ├── подключение к БД                 (планируется)
    ├── фабрика сессий БД                (планируется)
    ├── общий LLM
    ├── HTTP-клиенты                     (при необходимости)
    └── другие ресурсы приложения
            │
            ▼
        app.state
            │
            ▼
   api/dependencies/
            │
            ▼
     модули приложения
```

## 3. Структура всего проекта

```text
project/
├── api/
│   ├── app/
│   │   ├── api/
│   │   │   ├── endpoints/
│   │   │   │   └── optimization/
│   │   │   │       ├── router.py
│   │   │   │       │   # HTTP-обработчики запросов, связанных с запуском процесса.
│   │   │   │       │
│   │   │   │       └── schemas.py
│   │   │   │           # Pydantic-схемы входных данных и ответов API.
│   │   │   │
│   │   │   ├── dependencies/
│   │   │   │   ├── providers.py
│   │   │   │   │   # Получение ресурсов приложения:
│   │   │   │   │   # LLM, подключений к БД, HTTP-клиентов и т. д.
│   │   │   │   │
│   │   │   │   └── services.py
│   │   │   │       # Создание и передача сервисов, необходимых обработчикам.
│   │   │   │
│   │   │   └── router.py
│   │   │       # Общий маршрутизатор API.
│   │   │       # Подключает маршрутизаторы отдельных групп запросов.
│   │   │
│   │   ├── core/
│   │   │   ├── config.py
│   │   │   │   # Конфигурация приложения и подключаемых сервисов.
│   │   │   │
│   │   │   └── logger.py
│   │   │       # Единая настройка логирования приложения. (планируется)
│   │   │
│   │   ├── models/
│   │   │   ├── base.py
│   │   │   │   # Базовый класс SQLAlchemy-моделей. (планируется)
│   │   │   │
│   │   │   └── ...
│   │   │       # ORM-модели таблиц БД. (планируется)
│   │   │
│   │   ├── common/
│   │   │   ├── llm/
│   │   │   │   └── ...
│   │   │   │       # Общая инфраструктура работы с основной LLM сервиса.
│   │   │   │
│   │   │   ├── entities/
│   │   │   │   └── ...
│   │   │   │       # Структуры данных, используемые несколькими модулями.
│   │   │   │
│   │   │   ├── exceptions.py
│   │   │   │   # Исключения, используемые несколькими модулями.
│   │   │   │
│   │   │   └── enums.py
│   │   │       # Перечисления, используемые несколькими частями приложения.
│   │   │
│   │   └── modules/
│   │       ├── optimization_pipeline.py
│   │       │   # Верхнеуровневый код оркестрации процесса.
│   │       │   # Здесь находится run_pipeline(...).
│   │       │   # Вспомогательные части оркестратора лежат в orchestrator/.
│   │       │
│   │       ├── orchestrator/
│   │       │   └── ...
│   │       │       # Внутренние файлы оркестратора:
│   │       │       # состояние процесса, управление итерациями,
│   │       │       # условия продолжения и завершения и т. д.
│   │       │
│   │       ├── runner/
│   │       │   └── ...
│   │       │       # Код запуска оцениваемой системы
│   │       │       # и получения результатов выполнения.
│   │       │
│   │       ├── evaluator/
│   │       │   └── ...
│   │       │       # Код расчёта метрик и оценки результатов.
│   │       │       # Специфичные зависимости Ragas, в том числе его LLM-клиент,
│   │       │       # остаются внутри этого модуля.
│   │       │
│   │       ├── diagnostics/
│   │       │   └── ...
│   │       │       # Код анализа результатов запуска и оценки.
│   │       │
│   │       ├── optimizer/
│   │       │   └── ...
│   │       │       # Код формирования изменений для следующей итерации.
│   │       │
│   │       └── ...
│   │           # Другие модули по мере развития проекта.
│   │
│   ├── migrations/
│   │   └── ...
│   │       # Миграции схемы БД. (планируется)
│   │
│   ├── tests/
│   │   └── ...
│   │       # Модульные и интеграционные тесты.
│   │
│   ├── outputs/
│   │   └── ...
│   │       # Временное локальное хранение результатов работы.
│   │       # В дальнейшем постоянное хранение должно быть вынесено
│   │       # в БД или отдельное файловое/объектное хранилище.
│   │       # Папка не должна попадать в Git.
│   │
│   ├── run_server.py
│   │   # Создание FastAPI-приложения, lifespan,
│   │   # подключение маршрутизаторов и инициализация ресурсов.
│   │
│   ├── pyproject.toml
│   ├── requirements.txt
│   └── .pre-commit-config.yaml
```

---

### `common/`

В `common` выносится только код, который действительно используется несколькими модулями. Если компонент нужен только одному модулю, он остаётся внутри него.

### `models/`

`models` используется только для ORM-моделей БД. Pydantic-схемы API и внутренние сущности модулей сюда не помещаются.

### `outputs/`

`outputs/` — временная папка для локального сохранения результатов работы. В дальнейшем постоянное хранение следует вынести в БД или отдельное файловое/объектное хранилище. Папка не должна попадать в Git.

## 4. Рекомендуемая организация файлов внутри модуля

Пример структуры модуля:

```text
<module>/
├── service.py
│   # Основная логика модуля.
│
├── entities/
│   # Внутренние структуры данных модуля.
│
├── clients/
│   # Клиенты внешних сервисов, относящиеся только к этому модулю.
│
├── prompts/
│   # Промпты, используемые только этим модулем.
│
├── repository.py
│   # Работа с данными модуля в БД, если она требуется.
│
└── exceptions.py
    # Исключения, специфичные для этого модуля.
```
